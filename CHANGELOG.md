# Changelog

All notable changes to `qalainau/filament-warp-saas` are documented here.

## [Unreleased]

## [0.2.0] - 2026-11-26

### Added

- **AI gateway** (`app('warp.ai')`): the AI features of the Warp plugins ask Warp SaaS instead of a provider. It checks the team and its plan (`filament-warp-saas.ai.plans`), takes a seat with an estimate, calls the model of the tier with Laravel AI (`laravel/ai` is now required), records the real cost from the tokens and the price table, and keeps the cost of a failed call. Bound only when a model is set in the new config file. Commands `warp-saas:ai-check`, `warp-saas:ai-reconcile` (the providers' cost APIs) and `warp-ai:eval` (a plugin's AI cases against the real model); `WarpSaas::fakeAi()` for your tests; event `AiUsed`.
- `Meter::unavailableReason()`: whether the meter can be used now, without counting anything.
- **Seats for usage meters:** `Meter::reserve($tenant, $user, quantity: 1, estimate: 0)` checks the limits and takes the seat at once, under a cache lock per team and budget, and returns a `Reservation` (`complete(cost:, meta:)`, `fail(?cost)`, `cost()`). The budget check adds the estimate (`cost + estimate > budget`; with no estimate it is `≥` as before). `attempt()` accepts `estimate:` and passes the `Reservation` to the callback.

### Fixed

- **Many uses at the same moment no longer end in an error page:** when several people of the same company use a meter at once and one of them does not get the meter's lock within `Meter::$lockWaitSeconds` (5), `reserve()` and `attempt()` now throw `UsageBusy` (extends `LockTimeoutException`, a 503 with a “wait a moment and try again” message) instead of a bare `LockTimeoutException` (a 500). The AI gateway turns it into `AiUnavailable` with the reason `busy`, so plugins show that sentence. Translated into all 10 languages.
- **The AI gateway sent nested objects with no fields:** a plugin that wrote the `properties` of a nested object as `(object) [...]` (so an empty one is `{}` in JSON) had those fields dropped by Laravel AI's schema reader, so the model saw an empty object and filled nothing (Warp Input's Smart Paste, Warp Table's AI filter). The schema is now read through JSON first.
- **Usage meters let several uses at the same moment pass the last one:** `attempt()` checked, then called the API, then recorded, with no seat taken in between, so a team with 1 use left that pressed the button 8 times at once used 8. `attempt()` now takes a seat with `reserve()` first (it needs a cache store with locks; the `null` store throws a `LogicException`). `ensureAvailable()` and `record()` are unchanged.
- **Usage meters lost the cost of a failed use:** when the callback of `attempt()` threw after the provider had already charged (the answer could not be read, a timeout), nothing was recorded. A cost reported with `$reservation->cost(…)` is now kept with 0 uses, so it counts toward the budget.

- The tenant data map now knows `warp_scheduler_task_segments` (the split task parts of Warp Scheduler 1.18.0's `taskSplitting()`): its rows belong to the company of the task that owns them, like the other Warp Scheduler tables. Before, apps that check every table is classified failed once the table existed.

## [0.1.1] - 2026-11-22

### Fixed

- The billing history on an account's page now asks your policy for charges (`viewAny` for the section, `view` for each charge), like the charges resource does.

- **Operator invoice list follows the panel's time zone**: the "past due" filter and the minimum due date when creating an invoice used the app's UTC date, so with the admin panel set to e.g. America/New_York an invoice due today showed as past due during the UTC night. They now use the panel's time zone (`FilamentTimezone`).
- **Page access rules on a replaced page**: when the app replaced a standard page or resource with a subclass (`xxxPage()`/`xxxResource()`), `canAccessUsing()` and `canWriteUsing()` received the subclass as `$page`, so a rule such as `$page !== Projects::class` did not match and a page the app had closed still opened (HTTP 200). `$page` is now always the plugin's own standard class, whatever the app swaps in. A rule that compared `$page` with the app's own subclass must compare with the standard class instead.

## [0.1.0] - 2026-11-20

A first pre-release, for the author's own applications. Warp SaaS is not on sale yet.

### Fixed

- **Charges on PostgreSQL:** in `ChargeResource`, a team value that is not a number (sent from the browser) made a database error (500) on PostgreSQL. It is now treated as no team.
- **A card removed on Stripe:** after the saved card was detached (or the Stripe customer deleted), *Plan and usage* said *No card yet*, as if the company had never added one. It now says *The card was removed on Stripe. Add a card before the next invoice.* until a card is saved again.
- **Payments in the Stripe dashboard:** a card charge had no description, so a payment could not be matched to its invoice there. The PaymentIntent's description is now the invoice number.
- README: on SQLite, two webhook events at the same moment can make one fail with *database is locked* (Stripe sends it again); allow only cards in the customer portal's payment methods.
- **Card after a deleted Stripe customer:** after a customer was deleted in Stripe (`customer.deleted`), the team could not add a card for 24 hours (*No such customer*), because the customer was created with a fixed idempotency key and Stripe answered with the deleted customer. The customer is now made only when the saved one is empty, inside the account's row lock, with no fixed key.
- **Card payments with stripe-php 23:** Stripe Checkout could not be created (*The `payment_method_types` parameter is no longer supported*) because stripe-php 23 talks a newer Stripe API version. Warp SaaS now pins the Stripe API version (`Billing::STRIPE_API_VERSION`, `2026-02-25.clover`) on every request, whichever stripe-php (`^19` to `^23`) is installed, and `->stripe(apiVersion: …)` chooses another. Create your webhook endpoint with the same API version.
- **Failure reasons:** a decline with Stripe's `generic_decline` (and `do_not_honor`, `stolen_card` and the other bank codes) is now *the card was declined*, not *the payment could not be completed*. New reasons: wrong security code, wrong card number, a problem at the card company. The mail and the invoice show them in all 10 languages.
- **Right after the card page:** an invoice that the queue has not tried to charge yet shows *Checking the payment* instead of *Unpaid*.
- **Return page:** a `paid_session` or `card_session` of another team's Stripe Checkout no longer shows *We are confirming the payment* (nothing changes, and the warning is still logged).

### Added

- `Billing::customerPortal()` lets owners manage their company’s card on Stripe, with webhook updates for replaced cards and a test portal for `fakeCards()`.

- Card webhooks process each Stripe event ID once, with 90-day cleanup and retries after processing failures; detached payment methods and deleted customers clear the matching saved card without ending the contract.

- `Billing::activateOnCard()` lets owners of trial companies choose a plan and start their contract by saving a card on Checkout, with the first invoice charged through the existing card job.

- **`ChargeResource` on its own:** it can be registered in your own operator panel without `FilamentWarpSaasAdminPlugin`. `canAccess()` then uses the signed-in user, the billing setting and your `Charge` policy (`viewAny`); extend the class and override `canAccess()` / `isOperator()` to decide who is an operator. *Create an invoice* finds teams without the admin plugin too, and `createChargeAction(fn ($record) => $record)` can be placed on a team's edit page.
- `ChargeHistory::section()` and `InvoiceLinks::forTenant()` are public API (no longer `@internal`), with typed PHPDoc, for apps that replace the plan page with `->planPage(false)`.
- README: the order *price → `activate()`*, a note that ended teams need `getTenants()` to open their invoices.

### Changed

- `WarpSaas::setPrice()`, `setBillingMethod()`, `setBillingPeriod()` and `setAdditions()` create the account row when it is missing instead of throwing `ModelNotFoundException` (the row has the same defaults as no row).

- **Look-only mode:** a team can see everything and export its data but cannot change it. `WarpSaas::makeReadOnly($team, $note)`, `makeWritable()`, `isReadOnly()` and `whileWritable()`; `Overdue::ReadOnly` for `->whenOverdue()` (look-only after the due date and `graceDays()`, writable again when the unpaid invoices are paid or voided); `->readOnlyAfterEnd()` (an ended team can look and export until its data is deleted); `->readOnlyBanner()` and `->readOnlyAbilities()`. Changes are stopped in three places: `Gate::before` (also for Filament resources without a policy), `saving` and `deleting` of tenant models (`TenantReadOnly`, a 403), and the *Members* page. A query builder's `update()` and `delete()`, the plugin's own models and the operator panel are not stopped. The operator panel has *Make look-only* and *Make writable again* and a *Look-only* badge. Events `TenantMadeReadOnly` and `TenantMadeWritable`. New migration `update_warp_saas_accounts_add_read_only`.
- **After the trial:** `->afterTrial(AfterTrial::End | Activate | AskOwner)` and `WarpSaas::continueAfterTrial($team)` make a trial that runs out a contract (with the first invoice, dated the day after the last day of the trial) instead of ending the team. Owners switch it on *Plan and usage* (*Continue after the trial* / *End with the trial*), operators on the team's page. The contract is written by `warp-saas:notify-trials`, `warp-saas:bill` or the first page opened, once. Event `AfterTrialChanged`. Existing teams get `activates_after_trial = false`. New migration `update_warp_saas_accounts_add_after_trial`.
- **Card payments (Stripe):** `Billing::card()` and `Billing::methods(ChargeMethod ...)`, `->stripe()` and `->retryCardAfterDays([3, 5])`. Owners save a card on Stripe Checkout (the number never reaches your app); each invoice made by Warp SaaS is charged to it by a queued job; a failed payment mails the owners with a *Pay by card* button and is tried again on the given days. The webhook `POST /warp-saas/stripe/webhook` (`checkout.session.completed`, `payment_intent.succeeded`, `payment_intent.payment_failed`) checks the signature, team, customer, amount and currency, and pays an invoice once. Refunds and chargebacks are left to the Stripe dashboard. `WarpSaas::fakeCards()` replaces Stripe in tests and demos. Deleting a team deletes its Stripe customer. Event `CardPaymentFailed`. `stripe/stripe-php` is a `suggest`. New migration `update_warp_saas_add_cards`.
- `canAccessUsing()` and `canWriteUsing()` decide per page who can open *Members*, *Export data* and *Plan and usage*, and who can only look at *Members* (for your app's own roles). `$page` is your own class when you replaced the page (`->membersPage()`), and the *Pending invitations* table under *Members* asks with that same class.
- **Billing (invoices paid by bank transfer):** `->billing(Billing::invoice())` makes an invoice when a team starts its contract and at the start of every month or year after it (counted from that day in the team's time zone, so 31 January → 28 February → 31 March), with tax added or included and rounded as you choose, in the digits of the currency. `warp-saas:bill` makes the invoices that are due, reminds the owners before the due date, tells them when it is past due (`ChargeOverdue`) and after the grace days only reports it or ends the contract (`OverdueGraceEnded`); a team ended for an unpaid invoice is resumed when the payment is recorded. Owners see their invoices on the *Plan and usage* page and a red bar while one is past due; the operator panel gets the *Invoices* resource (record a payment, cancel, create one by hand) and a price and payment method per team. `issueInvoiceUsing()` lets your accounting system make the invoice, and `seller()` gives a simple printable invoice page. Invoices are kept when a team is deleted, are in its export zip, and `warp-saas:prune-charges` deletes them after `keepChargesFor()`. Without `billing()` nothing changes. A new migration `update_warp_saas_add_billing` adds the `warp_saas_charges` table and four columns to `warp_saas_accounts`.
- **Prepaid periods:** `WarpSaas::setBillingPeriod($team, 24)` bills a team for 24 months at once (1 to 120 months; whole years on a yearly plan; `null` = the plan's period), from its next invoice. The plan line and the monthly feature lines are multiplied by the months and a yearly price by the years, and the quantity is shown with its unit (*24 months × $29.00*). `WarpSaas::billingPeriodOf()` and `WarpSaas::paidUntil()` (the last day of the latest paid period) are new; *Plan and usage* and the operator's team page show the billing period, the discount and until when it is paid, and the operator's *Set the price and how they pay* has the billing period, how additions are billed and the discount. Run `php artisan migrate`: `update_warp_saas_accounts_add_billing_months` adds `billing_months`, `billing_additions` and `billing_discount`.
- **Changes in the middle of a period:** a plan upgrade or a new paid feature in the middle of a period longer than a month (a yearly plan, a prepaid period) is billed from the next month: `->additions(Additions::Monthly)` (the default) makes one invoice a month from `warp-saas:bill`, `Additions::Prorated` one invoice for the rest of the period, `Additions::NextCharge` waits for the next period invoice; per team with `WarpSaas::setAdditions()` and `WarpSaas::additionsFor()`. The month of the change is free, downgrades are not refunded, `linesUsing()` is not called for these invoices. `->prorateChanges(bool)` is a short way to choose `Prorated` or `NextCharge`. Monthly teams are not affected. `WarpSaas::changeTogether(fn () => …)` counts several changes as one (one `Prorated` invoice for two features); the operator's *Add or remove features* does this.
- **Prepaid discounts:** `->prepaidDiscounts([12 => '10%', 24 => '15%', 36 => 50000])` and `WarpSaas::setPrepaidDiscount($team, '20%')` add a discount line (`ChargeLine::DISCOUNT`, a minus amount) to the period invoices, before `linesUsing()`. A percent also applies to `Prorated` invoices.
- **Lines of an invoice:** `featurePrices()` gives a price to the features you add to a team on top of its plan (`grantFeature()`), and each becomes a line of the invoice — 12 × the monthly price on a yearly plan, and a yearly feature on a monthly plan is billed once a year (it stays paid when it is taken away and given back). `linesUsing()` lets your app return the lines (per seat, a discount) after the plugin's plan and feature lines; `setPrice()` replaces only the plan line and `setPrice(0)` still means no invoices. The lines are saved on the invoice, shown on the invoice page, in the mails, in the breakdown of the next invoice on *Plan and usage* and on the operator's team page; `charge(lines: [...])` and the operator's *Create an invoice* take several lines, and `upcomingLines()` and `$charge->lines()` read them. One tax rate for all lines. A new migration `update_warp_saas_charges_add_lines` adds `lines`, a unique index on `number` and the counter table.
- **Invoice numbers:** `numberUsing()` makes the invoice number from a running number of all invoices and one per year (`WW-2026-0001`), counted with locked rows inside the transaction that makes the invoice, so numbers never repeat; a canceled invoice keeps its number. `issueInvoiceUsing()` still wins when it returns a number.
- **Billing:** `warp-saas:bill` goes on with the other teams when making one team's invoice throws, reports it and ends with a failure code; that team is tried again the next time.
- **Operator panel:** the *Invoices* resource also asks your app's `Charge` policy (`viewAny`) when there is one.
- **Tenant data map:** `keepOnDelete()` marks a table whose rows are kept when a tenant is deleted.
- **Tenant data map:** `files(..., accept: fn ($tenant, $disk, $path) => …)` leaves out of the export and the deletion a file the row points to that is not the tenant's (a path a user typed, or another team's path). The reference guard runs at `saving` when the row's tenant is known, so a refused row never reaches the model's own `creating` (a number taken from a counter is not used up), and `WarpSaas::data()->checkReferences($model)` runs it by hand before your own `saving` side effects.
- **Members:** `invitationMailUsing()` adds lines to the plugin's invitation mail (where each role signs in) without replacing it.
- **Limits:** a model with `CountsTowardLimit` can say which rows count with `countsTowardLimit()`. A row that does not count (an inactive technician, a draft) can be created at the limit, and the limit is checked when an update makes it count.
- **Trials:** `trialBanner()` takes a function (`$panel`, `$tenant`, `$user`), so the bar can be left out of one of the panels that have the plugin.
- **Members:** `redirectAfterInvitationUsing()` decides where a person goes after joining from the invitation page. By default it is the team in the panel of the invitation page, which a role that uses another panel (a technician with a field panel of their own) cannot open.
- **Tenant isolation:** `BelongsToTenant` limits a model to the current tenant in the panel, in queued jobs and in commands. Outside the panels a query with no tenant throws `TenantNotSet` instead of returning every customer's rows; `WarpSaas::actingAs()`, `eachTenant()` and `withoutTenant()` say which tenant, or that you mean all. A new row gets the current tenant, a foreign key of another tenant (a form value edited in the browser) throws `TenantMismatch`, and a row cannot be moved. Queued jobs run as the tenant they were dispatched in and are not run for a tenant that has been deleted or has ended (`RunsForEndedTenants` lets chosen jobs through).
- **Tenant data map:** `WarpSaas::data()` tells Warp SaaS which tables are shared, which hang on a parent, which columns point to rows without a foreign key and which hold files. It refuses a row that points to another tenant's row before it is saved (`CrossTenantReference`), `warp-saas:check-references` checks the data that is already there, and `TenantDataAssertions` gives your test suite six checks that keep the data exportable and deletable. The tables of the other Warp plugins are included.
- **Plans, features and limits:** `Plan` with features, limits and a displayed price; `hasFeature()`, `limit()`, `changePlan()` (refused when the team has more than the new plan allows), `grantFeature()` and `setLimit()` per team. `RequiresFeature` stops a page in `canAccess()`, `EnforcesLimit` stops the create page and explains the limit on the button, `CountsTowardLimit` stops creates from jobs and imports, and a middleware `warp-saas.feature:` protects routes. The *Plan and usage* page shows it all to owners.
- **Trials and account status:** an account is Active, Trialing or Ended, decided in one place. `startTrial()`, `extendTrial()`, `activate()`, `end()` and `resume()`; days are counted in the team's time zone. A bar with the days left, a mail before the trial ends (`warp-saas:notify-trials`, at most one a day), and a page for ended teams that moves people to another team of theirs when there is one.
- **Members and invitations:** the *Members* page for owners, invitations by email with a token that is stored only as a hash, an accept page that needs a button press and the invited address, sign-up from the link for people without an account, your own roles, and the last owner can never be removed. Invitations count toward the `members` limit.
- **Data export and deletion:** a zip with one CSV per table and the files, secret columns left out and spreadsheet formulas neutralized, built row by row; the *Export data* page with signed, expiring downloads and a daily limit; `warp-saas:export`, `warp-saas:delete` and `warp-saas:purge`, which delete child rows first in batches, files before their rows and the tenant last, so an interrupted deletion can be run again.
- **Usage quotas:** `WarpSaas::meter()` stops an expensive feature by uses per month, money per month, a budget for the whole service (with a separate one for trials) and uses per minute, and records every use. `attempt()` checks, runs your code and records in one call.
- **Operator panel:** `FilamentWarpSaasAdminPlugin` adds the *Accounts* resource to a panel without tenancy: every team with its plan, state and members, and buttons to change the plan, features and limits, extend the trial, start or end the contract, export and delete.
- **Child tables:** `BelongsToTenantThrough` limits a model with no tenant column (the tasks of a project, the lines of an invoice) to the rows whose parent belongs to the current tenant, through any number of parents and through a polymorphic parent listed in `tenantParentTypes()`. Creating or moving a row under another tenant's parent throws `TenantMismatch`, also for models without the trait, and so does saving a row of another tenant read inside `withoutTenant()`.
- **Works with Filament's tenant scoping:** inside `actingAs()`, `withoutTenant()` and queued jobs, Filament's own tenant scope of a resource's model is removed from the query and Filament's resource no longer fills in the URL's tenant on create, so these functions return what they say even on a page of a scoped resource.
- **A trial until a date:** `startTrial(until: …)` ends the trial at a moment you give, read like `end()`, instead of counting days from today.
- **Your own answer for ended teams:** `whenAccountEnded()` gets the tenant, the account and the request by name; a response it returns is sent instead of the move to another team or the ended page.
- **Operator panels are named:** queries are no longer left unlimited in every panel without tenancy, only in the panel with `FilamentWarpSaasAdminPlugin` and the ones named with `operatorPanels()`. Any other panel without tenancy (a staff panel, a customer portal) is treated like code outside the panels: the tenant from `resolveTenantUsing()`, else `TenantNotSet`, so a forgotten resolver or a login page no longer returns every tenant's rows.
- **Usage quotas:** `reset()` gives a tenant a fresh month of one meter and `clearRateLimit()` forgets the per-minute count.
- **Invitations that fit your app:** `sendInvitationsUsing()` sends your own invitation mail (also when sending again), `invite(meta: [...])` keeps app fields such as a department on a waiting invitation and `invitedMemberPivotUsing()` puts them on the pivot when it is accepted, `invitationsExpireAfter(null)` makes invitations that never expire and keep counting toward the `members` limit, and `pendingInvitation()` / `pendingInvitationsFor()` find a waiting invitation without the token, for your own accept path. A new migration `update_warp_saas_invitations_add_meta` adds the `meta` column and lets `expires_at` be empty.
- **Usage quotas:** `sharesBudgetWith()` lets several meters share one money budget per month (and one trial budget), each with its own limit of uses. `budgetSpentThisMonth()` and `budgetReached()` tell where a meter stands.
- Twenty events, ten Artisan commands, and a translation in ten languages (English, Japanese, German, French, Spanish, Italian, Brazilian Portuguese, Korean, simplified and traditional Chinese).
